# mutiAI 前端交接说明

版本：V1 bootstrap

目标读者：前端开发者。

> **所有权说明（2026-07-28 更新）**：本文档最初写给在 Google AI Studio 中通过 GitHub 访问本仓库的 Gemini 协作者，后来由 Fable5 承担本地前端实现。
> 现在由 Codex 正式接手前端实现、真实后端集成、浏览器验收和修复提交。当前规则与交接入口请以
> `AGENTS.md` 和 `docs/CURRENT_STATUS.md` 为准；本文档的产品背景、页面范围和契约边界仍然有效。

## 1. 你正在参与什么项目

mutiAI 是一套可视化 AI 研发组织系统。普通用户不是直接与许多 Agent 对话，而是先与一个平台级“小助理”交流。小助理负责设计和管理用户拥有的 AI 组织；每个组织都有一个必须存在的组织负责人，组织负责人再管理组织内部已经存在的专业岗位。

长期目标是做成类似 Dify 的无限二维画布，让用户通过可视化方式构建复杂 AI 公司。但第一版不制作拖拽编辑器，先验证“对话设计组织、预览、确认、执行和查看进度”的完整闭环。

本仓库只负责 Web 前端。后端、产品数据库、LangGraph 编排层和 Codex Runtime 位于另一个仓库：

`https://github.com/Purewo/mutiAI`

后端仓库是产品契约的事实来源。不要依据自己的猜测创建接口或字段。

## 2. 第一版的确定边界

### 已确定

- 第一方界面是 Web 应用。
- M3 Web 核心闭环保持不变；M4 已授权接入个人微信连接页和统一渠道框架。
- 用户有一个平台级小助理。
- 每个组织必须存在一个组织负责人。
- 组织统一使用 `organization`，不要在页面中使用 `department` 表示同一概念。
- 用户可以和小助理对话，让它生成一个或多个组织方案。
- 用户确认之前只显示预览，不发布。
- 组织图必须由程序根据结构化数据渲染，不能用图片生成模型生成一张组织架构图。
- 确认后发布 `OrganizationSpec` 版本。
- 发布组织不会立即创建工作目录或 Codex Thread。
- 用户真正提交任务后才懒加载工作目录和 Runtime。
- 第一版只接入本地 Codex。
- 组织管理页第一版只读，显示组织图、岗位和工作进度。
- 组织详情页需要可以和该组织负责人对话。
- 第一版不做拖拽编辑器、无限画布编辑、成员邀请、多人协作、人工成员节点和 Agent 自主创建正式岗位。
- 知识库先保留入口或占位，不是第一版核心验收能力。

### 账户边界

产品资源按用户隔离。每个组织在 V1 只有一个 owner，不存在成员、邀请和共享组织。开发环境预置 `admin` 账号，简单密码只用于 localhost 测试，不能假设这种密码可以在网络环境中使用。

## 3. 产品层级

```text
用户
└── 平台小助理
    ├── 组织 A
    │   └── 组织负责人
    │       ├── 后端开发岗位
    │       ├── 前端开发岗位
    │       └── 测试岗位
    └── 组织 B
        └── 组织负责人
```

小助理不是某个组织的成员。它是平台控制层入口，可以查询用户拥有的组织状态，也可以在用户要求时向组织负责人下达任务。

组织负责人是组织内部的协调者，负责拆解、分配、检查和汇总。组织负责人不需要主动向小助理发送聊天式汇报；产品服务保存任务和事件数据，小助理需要时查询即可。

## 4. 第一版页面范围

左侧使用固定导航，右侧是当前内容。整体可以参考 ChatGPT 或 OpenClaw 的经典布局，但不要复制品牌视觉。

### 4.1 登录页

开发阶段使用预置 admin 账号完成测试。登录页需要保留明确的加载、失败和退出状态。是否在第一个前端迭代就实现注册页面，以核心仓库最终的 V1 任务为准，不要自行推断。

### 4.2 小助理页

这是用户进入系统后的主要入口。

需要支持：

- 展示与小助理的对话。
- 输入用户的组织需求。
- 展示小助理返回的结构化组织方案说明。
- 多方案切换或并列预览。
- 显示当前方案是否等待用户确认。
- 用户确认前允许继续对话修改。
- 用户确认后显示发布成功结果，并引导进入组织管理。

不要把组织方案只渲染成一段 Markdown。页面需要保留结构化数据驱动的组织预览区域。

### 4.3 组织管理页

显示当前用户拥有的组织卡片。卡片至少需要区分组织名称、负责人和整体工作状态，但具体字段以核心仓库契约为准。

第一版不做手动编辑组织，不做拖拽连线。页面可以提供查看详情、打开负责人对话和查看进度的入口。

### 4.4 组织详情页

页面主体包含：

- 组织名称和基本信息。
- 程序渲染的组织关系图。
- 组织负责人和已有岗位。
- 每个岗位当前状态或当前任务。
- 任务进度区域。
- 与组织负责人对话的聊天框。

组织图要适应不同数量的岗位。不要假设只有固定的前端、后端和测试三个节点。必须从结构化 Organization 数据绘制。

### 4.5 任务进度

用户提交任务后不能只显示一个无限旋转的 Loading。需要展示当前进度、正在执行的岗位、等待状态、失败状态和完成状态，前提是这些状态已经出现在正式事件契约中。

任务进度可能来自 SSE 或其他事件流。前端应该处理断线、重新连接和重复事件，不能把每个事件都简单追加成重复消息。

### 4.6 微信渠道对接页

M4 已提供正式 `/api/v1/channels/...` 契约。页面可以创建 `weixin-ilink`
连接、发起限时二维码授权、轮询明确的授权状态、管理允许的发送者身份，并查看
产品持久化的入站 journal 与出站 outbox 状态。当前只支持个人直聊文字；图片、
语音、文件、视频、群聊、卡片和反应不得显示为已支持。拿到二维码不等于账号已
连接，只有后端返回 `confirmed` / `connected` 后才可以展示成功状态。

### 4.7 知识库页

第一版可以是明确的占位页。不要为了填充页面而虚构文档上传、向量检索或知识更新接口。

### 4.8 个人中心

第一版只要求最基本的昵称和密码修改入口。提交成功、旧密码错误和未登录状态都需要有明确反馈。

## 5. 交互和视觉方向

- 左侧导航稳定，右侧内容区域承担主要工作。
- 组织图和任务状态是产品的核心视觉，不要让它们被装饰性面板淹没。
- 对话页面要区分用户、小助理、组织负责人和系统事件。
- 结构化方案要能看出负责人和岗位层级。
- 在数据尚未完成时使用明确的 skeleton、empty state 或 placeholder，不要伪造已经完成的 Agent 工作。
- 长文本、任务进度、错误消息和连接状态要有清晰层次。
- 视觉可以参考成熟产品的布局，但不要直接复制 Dify、ChatGPT 或 OpenClaw 的品牌资产。

## 6. 前后端协作规则

后端仓库 `Purewo/mutiAI` 是以下内容的唯一事实源：

- OpenAPI。
- `OrganizationSpec` 和相关 JSON Schema。
- 任务和 Agent 的状态定义。
- SSE 或其他事件的结构。
- 鉴权和错误格式。

前端仓库只消费生成的 TypeScript 类型、客户端或带来源 commit 的契约快照。不要在前端手写一份同名但字段不同的 `Organization`、`Task` 或 `Agent` 类型。

每次前端任务应当附带：

1. 页面目标。
2. 路由。
3. 允许修改的目录。
4. 核心仓库契约 commit。
5. API 和事件样例。
6. Loading、Empty、Error 和 Reconnect 行为。
7. 验收条件。
8. 明确不包含的内容。

如果契约中缺少一个前端必须知道的字段，请提出问题或使用临时视觉占位，不要自行创造后端字段。

## 7. GitHub 工作方式

> 本节的远程协作流程已由 Codex 的本地开发流程取代，参见 `AGENTS.md`、`docs/CURRENT_STATUS.md` 和
> `docs/LOCAL_INTEGRATION_REVIEW.md`。
> 分支粒度和提交说明的要求仍然适用。

前端代码应当提交到专用分支或 Pull Request，不要直接把未验证的实现合入 `main`。

推荐提交粒度：

- 一个页面或一个明确的用户流程。
- 不要在同一个提交中同时重写路由、设计系统、聊天状态和所有页面。
- 提交说明写清楚使用了哪个契约版本。
- 如果因为缺少后端接口使用了 Mock，明确列出 Mock 的边界。

每个前端改动在本地需要：

- 安装依赖并运行类型检查、lint 和构建。
- 连接真实后端。
- 检查浏览器控制台、网络请求和事件流。
- 验证关键交互和响应式布局。

“代码已经提交”不等于“功能已经完成”。联调使用本机后端和浏览器即可，不要求部署远程服务器。契约缺陷属于后端，
在 `Purewo/mutiAI` 中单独提交修复后再刷新本仓库的契约快照。

## 8. 当前不要提前实现的内容

- 无限二维画布。
- 复杂拖拽编辑器。
- 让 Agent 自主创建持久岗位。
- 多用户共享组织。
- 多 Runtime 厂商切换界面。
- 知识库完整产品。
- 假想的实时数据和假任务结果。

## 9. 需要等待核心仓库确认的技术选择

在核心仓库完成接口和技术选型前，不要擅自冻结以下内容：

- 前端框架和构建工具。
- 组织图渲染库。
- 全局状态管理方案。
- SSE 客户端封装。
- 组件库和最终品牌颜色。
- 真实 API 路径和状态枚举。

你可以先提交 UI 方案、静态结构、组件拆分和 Mock 驱动的交互实验，但要把这些选择标记为候选，而不是已经批准的系统事实。

## 10. 交付标准

一个前端任务只有满足以下条件，才可以标记为完成：

- 使用正式或明确标记的 Mock 契约。
- 不存在未声明的假 API 或假状态。
- 具备必要的加载、空、错误和连接中断反馈。
- 通过类型检查和项目测试。
- 能够与真实后端联调。
- 在浏览器中验证主要交互、控制台和网络请求。
- 提交说明包含已知限制和后续依赖。
